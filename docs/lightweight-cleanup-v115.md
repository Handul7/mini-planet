# v115 경량화 정리 및 검증

## 결론

전체 정적 배포본은 약 3.56 MiB에서 3.55 MiB로 줄었습니다. 파일 용량 자체가 과도한 상태는 아니며, 실행 중 부하는 3D 화면 해상도, 그림자, 발광 후처리의 영향이 더 큽니다. 이번 작업은 배치와 디자인을 유지하면서 초기 로딩과 반복 계산 비용을 줄이는 데 집중했습니다.

새 엔진, 번들러, 외부 라이브러리는 추가하지 않았습니다. v113 서비스 연결과 v114 계절·날씨 변경은 유지했습니다. 커밋과 외부 배포는 하지 않았습니다.

발광 후처리 축소는 외곽의 빛 번짐만 조절합니다. 종이 재질, 오브젝트 형태, 빛을 내는 창문 자체, 그림자, 날씨와 계절은 유지합니다. high 등급의 발광 해상도와 강도는 기존과 동일합니다.

모델은 처음 사용할 때 네트워크가 필요합니다. 모델 파일 자체는 이전에도 선캐시 대상이 아니었으며, 방문 중 불러온 리소스는 기존 서비스 워커 정책으로 캐시됩니다. 이번 작업에서 오프라인 편집을 새로운 기능으로 보장하지는 않습니다.

## 삭제하지 않은 항목

- 편집 팔레트의 GLTF 소품 9종: 우물, 풍차, 물레방아, 울타리, 나무통, 수련, 가로등, 호박, 벤치. 기본 배치에 없더라도 사용 가능한 기능입니다.
- 여러 모델이 함께 쓰는 텍스처, 아이콘, 공유용 OG 이미지, 글꼴과 라이선스.
- 이전 저장 배치를 현재 구조로 옮기는 마이그레이션 코드. 단순히 오래된 코드라는 이유로 지우면 사용자 배치가 손상될 수 있습니다.
- `_site` 등의 생성 결과물과 작업 보고서. 런타임 중복 로딩과는 구분했습니다. 이번 배포본 검사는 별도 임시 디렉터리에서 수행했습니다.

## 검증 결과

- 전체 자동 테스트: 275개 통과, 실패 0개.
- 새 회귀 테스트: 13개. 회피 계산은 기존 수식과 1,600개 배치에서 결과 오차 `1e-12` 이내로 일치했습니다.
- 모델 prototype·재질 공유, 텍스처 보존, 실패 후 재시도, 화질 자동 하향·복귀, 화면 크기 변경을 검증했습니다.
- 남아 있는 모델·바이너리·텍스처는 편집 등록표에서 모두 참조됩니다. 검사 범위의 byte-identical 파일과 중복 버전 정적 import는 없습니다.
- 배포 전 검사 및 최소 정적 artifact 검사 통과: 94개 파일, 3.55 MiB.
- 브라우저: 1280×800 데스크톱, 390×844 모바일 크기에서 캔버스 비어 있지 않음 확인. 샘플 색상 수는 각각 42개, 31개였습니다.
- 마을 29개 오브젝트, 여섯 집의 접근성, 길 연결, 배 승하선·왕복 항해, 바다 도보 진입 제한 검사 통과.
- 저사양 설정에서 눈 96개 표시와 겨울 표면 유지, 모바일 가로 넘침 없음, 콘솔 오류·경고 없음.
- 별도 테스트 주소에서 우물 추가·렌더링·실행 취소 확인. 기본 상태는 모델 로더 미요청/캐시 0개, 추가 후 요청/캐시 1개였습니다. 실제 사용자 저장 배치는 편집하지 않았습니다.

## 성능 해석과 남은 범위

저사양 설정의 로컬 데스크톱 및 모바일 크기 검증에서는 약 60 FPS가 관찰됐습니다. 이는 현재 Mac의 브라우저에서 측정한 값이며 실제 저가형 휴대폰의 성능 보장은 아닙니다. 동시에 열린 화면, 에이전트의 위치, 그림자 갱신 프레임에 따라 draw call이 달라지므로 한 프레임의 전후 차이를 최적화 효과 전체로 계산하지 않았습니다.

Retina 해상도의 balanced 강제 설정에서는 약 35~39 FPS도 관찰됐습니다. 따라서 모든 기기에서 high/balanced를 강제하기보다 기존 자동 화질 하향을 유지하는 편이 적절합니다. 실제 M1 서버가 그림을 렌더링하는 구조가 아니라 각 접속자의 브라우저가 Three.js 렌더링을 담당합니다. 서버 전송량은 줄일 수 있지만 클라이언트 GPU 성능까지 서버 설정만으로 해결할 수는 없습니다.

`main.js`는 여전히 큰 파일입니다. 파일을 나누는 것만으로 다운로드 용량이나 프레임 비용이 줄지는 않으므로, 이번에는 매 프레임 실행되는 간격 계산만 테스트 가능한 작은 모듈로 옮겼습니다. 이후 구조 정리가 필요하면 편집기와 배치 마이그레이션을 별도 책임으로 분리하되, 저장 호환 테스트를 유지하는 방식이 적절합니다.
